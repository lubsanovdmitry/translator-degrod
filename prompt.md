Создай полноценный локально запускаемый проект на Python 3.12 для экспериментального рекурсивного искажения художественных и документальных текстов посредством многократного машинного перевода и необязательной LLM-реконструкции.

Рабочее название проекта: `semantic-telephone`.

## 1. Общая цель

Система должна принимать пользовательский текст и многократно пропускать его через настраиваемый конвейер преобразований:

1. разбиение на содержательные блоки;
2. последовательные переводы через несколько языков;
3. необязательное грамматическое исправление;
4. необязательное восстановление связности с помощью LLM;
5. повторение цикла несколько раз;
6. сохранение всех промежуточных поколений;
7. сравнение результатов разных режимов.

Цель проекта — исследовать, как текст:

* теряет исходные значения;
* сохраняет общую структуру сцен;
* мутирует на уровне имён и терминов;
* приобретает новые причинно-следственные связи;
* самостоятельно формирует повторяющиеся семантические мотивы;
* иногда сохраняет собственные ошибки между фрагментами.

Это не должен быть генератор случайного сюрреализма, пародий или заранее заданного «чёрного юмора».

## 2. Ключевой принцип

Не добавляй в код заранее заданный псевдоканон.

Запрещено жёстко прописывать правила вроде:

* определённый персонаж всегда пьёт;
* конкретное имя превращается в страну;
* конкретное место становится жилым домом;
* конкретный персонаж постоянно бегает;
* при появлении определённой страны возникают связанные с ней стереотипы.

Все повторяющиеся мотивы должны возникать только из:

* многократных переводов;
* одинаковых или похожих маршрутов перевода;
* повторной обработки уже повреждённого текста;
* контекста предыдущих повреждённых фрагментов;
* необязательной автоматически извлекаемой памяти.

По умолчанию отдельная долговременная память должна быть выключена.

## 3. Технические требования

Используй:

* Python 3.12;
* строгую типизацию;
* `dataclasses` или Pydantic для моделей конфигурации;
* Typer или argparse для CLI;
* YAML для пользовательских конфигураций;
* JSONL для подробных журналов;
* pytest для тестов;
* стандартный `logging` с удобным выводом в консоль;
* асинхронный код там, где это оправдано для API-запросов;
* атомарную запись файлов;
* возможность продолжить прерванный запуск.

Не привязывай архитектуру к одному API или одной модели.

Сделай абстракции:

```python
class TranslationProvider(Protocol):
    async def translate(
        self,
        text: str,
        source_language: str,
        target_language: str,
        *,
        seed: int | None = None,
    ) -> TranslationResult:
        ...


class TextGenerationProvider(Protocol):
    async def generate(
        self,
        prompt: str,
        *,
        temperature: float,
        seed: int | None = None,
        response_format: str = "text",
    ) -> GenerationResult:
        ...
```

Минимально реализуй:

1. `MockTranslationProvider`;
2. `MockGenerationProvider`;
3. один локальный или API-ориентированный переводческий провайдер;
4. один OpenAI-compatible LLM-провайдер, настраиваемый через:

   * base URL;
   * API key;
   * model name.

API-ключи должны читаться только из переменных окружения или `.env`, который внесён в `.gitignore`.

## 6. Разбиение текста

Реализуй несколько стратегий:

1. `paragraph`;
2. `target_chars`;
3. `target_tokens`;
4. `sentence_window`.

Рекомендуемая стратегия по умолчанию:

* не разрывать абзацы без необходимости;
* целевой размер блока: 800–1400 символов;
* максимальный размер: 2200 символов;
* контекстное перекрытие: 1–2 предыдущих абзаца;
* перекрытие не должно дублироваться в финальном результате.

Контекст и основной текст блока должны храниться отдельно.

Система должна различать:

* текст, который необходимо преобразовать;
* текст, который передаётся модели только как контекст.

## 7. Генерация маршрутов перевода

Создай модуль генерации языковых маршрутов.

Поддержи режимы:

### `fixed`

Для всех блоков используется один маршрут.

Пример:

```yaml
languages:
  - ru
  - ka
  - ar
  - ja
  - hr
  - sw
  - de
  - hi
  - en
  - ru
```

### `random`

Маршрут генерируется случайно для каждого блока или цикла.

### `stratified`

Языки выбираются по категориям:

* германские;
* романские;
* славянские;
* агглютинативные;
* семитские;
* языки с нелатинской письменностью;
* низкоресурсные языки;
* промежуточный английский.

### `hubbed`

После каждого одного или нескольких языков текст возвращается через заданный hub-язык, обычно английский.

### `mutating_fixed`

Основной маршрут одинаков, но несколько языков случайно заменяются.

Все маршруты должны:

* логироваться;
* воспроизводиться по seed;
* исключать подряд идущий перевод языка в самого себя;
* завершаться целевым языком;
* поддерживать белые и чёрные списки языков.

Не утверждай, что какой-либо язык гарантированно производит более смешной результат. Это экспериментальный параметр.

## 8. Обязательные режимы работы

Реализуй минимум пять режимов.

### Режим A: `translate_only`

Конвейер:

```text
исходный блок
→ N последовательных переводов
→ конечный язык
```

Никакая LLM-реконструкция не применяется.

Назначение:

* получить чистый переводческий распад;
* измерить мутацию имён;
* увидеть потерю синтаксиса;
* сравнить переводческие маршруты.

### Режим B: `sparse_repair`

Конвейер:

```text
переводческий цикл
→ консервативное грамматическое исправление
→ второй переводческий цикл
→ конечный язык
```

Исправление должно:

* делать текст грамматически читаемым;
* не восстанавливать известный оригинал;
* не добавлять новые события без необходимости;
* сохранять странные имена, объекты и утверждения;
* не пытаться сделать текст смешным.

### Режим C: `iterative_reconstruction`

Конвейер:

```text
переводческий цикл
→ умеренная реконструкция связности
→ переводческий цикл
→ умеренная реконструкция связности
→ финальный перевод
```

Реконструктор может:

* добавлять пропущенные связки;
* определять наиболее вероятного говорящего;
* соединять оборванные действия;
* устранять чисто грамматические противоречия.

Реконструктор не должен:

* получать исходный текст;
* получать название известного произведения;
* исправлять имена по канону;
* получать инструкцию «добавить абсурд»;
* получать темы, которые надо вставить;
* превращать текст в намеренную пародию.

### Режим D: `rolling_context`

Как `iterative_reconstruction`, но LLM получает ограниченный хвост предыдущих повреждённых результатов.

Контекст должен состоять только из результатов системы, а не из оригинала.

Настройки:

* число предыдущих блоков;
* максимальный размер контекста;
* стратегия обрезки;
* использовать ли только финальные результаты блоков;
* использовать ли промежуточные поколения.

Предыдущий текст передаётся как ненадёжный контекст мира.

Нельзя давать модели инструкцию обязательно повторять старые мотивы.

### Режим E: `inferred_memory`

Экспериментальный и выключенный по умолчанию режим.

После каждого обработанного блока отдельный этап извлекает наблюдения:

* варианты имён;
* повторяющиеся свойства сущностей;
* повторяющиеся объекты;
* повторяющиеся места;
* повторяющиеся причинные ассоциации;
* возможные противоречия.

Память не является каноном и не должна формулироваться как абсолютные правила.

Пример внутренней записи:

```json
{
  "entity_key": "variant:example-name",
  "observations": [
    "персонаж дважды оказался связан с непрерывным движением",
    "имя один раз было переведено как название предмета"
  ],
  "count": 2,
  "confidence": 0.31,
  "first_seen_chunk": 4,
  "last_seen_chunk": 11,
  "weight": 0.24
}
```

Требования:

* записи создаются только автоматически;
* память может ошибаться;
* память имеет decay;
* одноразовые наблюдения быстро забываются;
* повторения повышают вес;
* память может быть полностью проигнорирована реконструктором;
* память не должна содержать заранее созданных примеров;
* пользователь может посмотреть, очистить или выключить память;
* запуск без памяти остаётся основным режимом.

Формула decay может быть простой и документированной, например:

```text
weight = confidence × log(1 + count) × exp(-age / half_life)
```

Не используй эту формулу как научно доказанную — это только эвристика.

## 9. Промпты для LLM

Храни промпты в отдельных текстовых файлах.

### 9.1. Консервативное исправление

Используй основу:

```text
Ты исправляешь фрагмент художественного текста, повреждённый
машинным переводом.

Задача:
- исправить явные грамматические разрывы;
- сделать предложения читаемыми;
- по возможности сохранить порядок реплик и действий;
- сохранить все необычные имена, предметы и утверждения;
- не определять исходное произведение;
- не восстанавливать канонические имена;
- не сверяться с известным сюжетом;
- не добавлять юмор, сатиру, мораль или комментарии;
- не объяснять странности;
- не добавлять новые события, если без них текст уже можно прочитать.

Верни только исправленный текст.
```

### 9.2. Умеренная реконструкция

Используй основу:

```text
Перед тобой фрагмент текста после нескольких циклов машинного перевода.
Оригинал недоступен.

Восстанови локальную связность текста, исходя только из данного фрагмента.

Правила:
- сохрани примерный порядок событий и реплик;
- считай странные имена, объекты и утверждения возможными фактами текста;
- не пытайся определить известный оригинал;
- не исправляй текст по памяти о книгах, фильмах или других произведениях;
- не возвращай предполагаемые исходные имена;
- заполняй только необходимые смысловые переходы;
- не создавай намеренную пародию;
- не пытайся сделать результат смешным или шокирующим;
- не вставляй заранее заданные темы;
- противоречия допустимы, если их нельзя устранить локально;
- повествователь не должен комментировать странность происходящего;
- по возможности сохрани объём текста в пределах 80–120% от входного.

Верни только реконструированный текст.
```

### 9.3. Реконструкция с предыдущим контекстом

Используй основу:

```text
Ниже даны:

1. предыдущий повреждённый текст;
2. новый повреждённый фрагмент.

Предыдущий текст является ненадёжным контекстом, а не каноном.
Он может содержать ошибки, противоречия и случайные мутации.

Исправь и локально свяжи только новый фрагмент.

Правила:
- предыдущий текст не повторяй;
- не продолжай старые мотивы без основания в новом фрагменте;
- если новая странность естественно совпадает с предыдущей, её можно сохранить;
- не делай соответствия обязательными;
- не устраняй противоречия между фрагментами любой ценой;
- не восстанавливай предполагаемый оригинал;
- не добавляй юмор или тематические мотивы намеренно;
- верни только обработанный новый фрагмент.
```

### 9.4. Автоматическое извлечение памяти

Ответ должен быть строго JSON.

Промпт должен требовать:

* записывать только факты, присутствующие в повреждённых результатах;
* отличать варианты имени от свойств персонажа;
* не использовать знания об оригинале;
* не создавать наблюдение после единственного слабого намёка, если оно несущественно;
* отмечать уверенность;
* не объявлять наблюдения законами мира.

Проверь JSON через схему и повтори запрос при невалидном ответе.

## 10. Вероятностное применение этапов

Каждый необязательный этап должен поддерживать вероятность применения.

Пример:

```yaml
stages:
  - type: translation_cycle
    repeat: 1
    hops:
      min: 5
      max: 9

  - type: conservative_repair
    probability: 0.35

  - type: translation_cycle
    repeat: 1
    hops:
      min: 4
      max: 7

  - type: contextual_reconstruction
    probability: 0.65
```

Решения должны быть воспроизводимы по seed и записываться в журнал.

## 11. Конфигурация YAML

Пример:

```yaml

│   │   ├── stage-01-output.txt
│   │   ├── stage-02-repair.json
│   │   ├── stage-02-output.txt
│   │   └── final.txt
│   └── 0002/
└── memory/
    ├── observations.jsonl
    └── state.json
```

Сохраняй результат после каждого этапа.

При прерывании программа должна продолжать с последнего полностью завершённого этапа.

Используй checksum входа, конфигурации этапа и модели для определения, можно ли переиспользовать checkpoint.

## 13. Экспериментальная матрица

Реализуй команду, которая запускает один исходный текст в нескольких режимах.

Пример матрицы:

```yaml
experiment:
  name: baseline-comparison
  repetitions: 3
  seeds:
    - 100
    - 200
    - 300

variants:
  - name: translation-only
    config: configs/translate_only.yaml

  - name: sparse-repair
    config: configs/sparse_repair.yaml

  - name: iterative-reconstruction
    config: configs/iterative_reconstruction.yaml

  - name: rolling-context
    config: configs/rolling_context.yaml

  - name: inferred-memory
    config: configs/inferred_memory.yaml
```

Матрица должна создавать:

* отдельные каталоги запусков;
* общий Markdown-отчёт;
* сводную CSV или JSON-таблицу;
* ссылки на финальные тексты;
* сравнение метрик;
* таблицу параметров;
* информацию о стоимости API, если провайдер возвращает usage.

## 14. Метрики

Метрики являются диагностическими и не должны объявляться объективной оценкой художественного качества.

Реализуй минимум:

### Структурные

* отношение длины результата к оригиналу;
* количество абзацев;
* количество предложений;
* количество строк диалога;
* число кавычек и тире диалога;
* доля пустых или оборванных предложений.

### Лексические

* token overlap;
* character n-gram similarity;
* доля новых слов;
* повторяемость слов и фраз;
* частота повторяющихся n-грамм;
* изменение регистра и пунктуации.

### Семантические

Если доступна embedding-модель:

* сходство результата с оригиналом;
* сходство соседних поколений;
* скорость семантического дрейфа по этапам.

Embedding-метрики должны быть необязательными.

### Мутации сущностей

Не используй сложный NER как обязательную зависимость.

Реализуй простую эвристику:

* слова с заглавной буквы;
* повторяющиеся необычные токены;
* слова после реплик обращения;
* последовательности предполагаемых имён.

Показывай:

* наиболее частые варианты;
* расхождение форм;
* повторные превращения одного токена;
* устойчивые варианты в разных блоках.

### Генеративное расширение

Эвристически оцени:

* рост длины;
* появление новых предложений;
* новые сущности;
* новые числа, даты, бренды и географические названия;
* фрагменты результата, не имеющие очевидного лексического соответствия входу.

Не называй это доказательством галлюцинации. Используй формулировку «возможное генеративное расширение».

## 15. CLI

Реализуй команды:

```bash
semantic-telephone init
semantic-telephone validate CONFIG
semantic-telephone run CONFIG
semantic-telephone resume RUN_DIRECTORY
semantic-telephone matrix MATRIX_CONFIG
semantic-telephone inspect RUN_DIRECTORY
semantic-telephone compare RUN_A RUN_B
semantic-telephone report RUN_DIRECTORY
semantic-telephone memory show RUN_DIRECTORY
semantic-telephone memory clear RUN_DIRECTORY
```

### `init`

Создаёт:

* пример `.env`;
* пример конфигурации;
* пустой `input.txt`;
* краткую инструкцию.

### `run`

Показывает:

* текущий блок;
* текущий этап;
* маршрут перевода;
* прогресс;
* количество повторных попыток;
* путь к checkpoint.

### `inspect`

Показывает историю одного блока:

```text
Original
→ Translation cycle 1
→ Repair
→ Translation cycle 2
→ Reconstruction
→ Final
```

Добавь параметр `--chunk`.

### `compare`

Создаёт side-by-side Markdown или HTML diff между:

* двумя запусками;
* двумя поколениями;
* оригиналом и финалом.

## 16. Отчёт

Автоматически создавай `report.md`.

Структура:

1. конфигурация;
2. описание режима;
3. языковые маршруты;
4. сводные метрики;
5. примеры наиболее изменившихся фрагментов;
6. повторяющиеся варианты сущностей;
7. возможные генеративные расширения;
8. предупреждения;
9. информация о воспроизводимости;
10. стоимость и число запросов, если известны.

Не интерпретируй результат как научно доказанный эффект.

## 17. Обработка ошибок

Нужно корректно обрабатывать:

* таймауты;
* rate limits;
* отказ провайдера;
* пустой ответ;
* ответ не на ожидаемом языке;
* чрезмерно длинный ответ;
* невалидный JSON;
* частично переведённый текст;
* отсутствие поддержки языковой пары;
* достижение контекстного лимита;
* прерывание пользователем.

После нескольких неудачных попыток:

* сохрани ошибку;
* не уничтожай предыдущие результаты;
* разреши выбрать `skip`, `stop` или fallback-провайдер;
* в автоматическом режиме используй политику из конфигурации.

## 18. Ограничения и защита эксперимента от подделки

Добавь автоматические проверки:

1. В стандартных промптах не должно быть заранее заданных сюжетных мотивов.
2. Стандартные промпты не должны содержать слова вроде:

   * «сделай смешнее»;
   * «добавь абсурда»;
   * «добавь чёрный юмор»;
   * «добавь алкоголь»;
   * «добавь политику»;
   * «добавь насилие».
3. Реконструктор не должен получать исходный блок одновременно с повреждённым.
4. Предыдущий оригинальный текст не должен использоваться как контекст.
5. Память по умолчанию выключена.
6. Автоматическая память не должна создаваться из исходного текста.
7. Любой пользовательский кастомный промпт должен отмечаться в manifest.
8. Изменения стандартных промптов должны менять checksum запуска.

Добавь тест, проверяющий отсутствие заранее заданного псевдоканона в стандартных конфигурациях и промптах.

## 19. Воспроизводимость

Один seed должен управлять:

* выбором маршрута;
* выбором числа переходов;
* вероятностным включением этапов;
* выбором контекстных блоков;
* порядком необязательных операций.

Если внешний API не поддерживает seed или не гарантирует детерминизм, явно записывай это в manifest.

Сохраняй:

* название модели;
* параметры генерации;
* endpoint;
* дату;
* идентификатор ответа API, если доступен;
* usage;
* хеш промпта;
* хеш входа и выхода.

## 20. Тесты

Напиши полноценные тесты.

Обязательные unit-тесты:

* разбиение текста без потери абзацев;
* отсутствие дублирования overlap в финальном файле;
* воспроизводимость маршрута по seed;
* отсутствие одинаковых соседних языков;
* возврат к целевому языку;
* валидация YAML;
* сериализация manifest;
* сохранение checkpoint;
* продолжение прерванного запуска;
* decay автоматической памяти;
* невозможность заполнить память из исходного текста;
* корректная работа mock-провайдеров;
* обработка пустого ответа;
* обработка невалидного JSON;
* отсутствие жёстко заданных мотивов в стандартных промптах.

Интеграционные тесты должны использовать mock-провайдеры и не требовать сетевого подключения.

Создай небольшой искусственный тестовый текст, написанный специально для проекта. Не включай в репозиторий большие фрагменты защищённых авторским правом произведений.

## 21. Mock-провайдеры

Mock-переводчик должен уметь детерминированно:

* менять некоторые слова местами;
* иногда переводить имя как обычное слово;
* удалять местоимения;
* менять род;
* повторять короткую фразу;
* заменять термин похожим словом;
* портить пунктуацию.

Mock-LLM должен детерминированно:

* соединять оборванные предложения;
* добавлять ограниченное число связок;
* не добавлять заранее заданных тематических мотивов.

Это необходимо для воспроизводимых тестов конвейера.

## 22. README

README должен включать:

* назначение проекта;
* предупреждение, что качество зависит от провайдеров;
* установку;
* настройку `.env`;
* быстрый старт;
* описание пяти режимов;
* пример YAML;
* команды CLI;
* структуру результатов;
* объяснение rolling context;
* объяснение автоматической памяти;
* объяснение, почему память выключена по умолчанию;
* руководство по экспериментальной матрице;
* информацию о воспроизводимости;
* ограничения;
* раздел «Why this is not a random absurdity generator».

Подчеркни:

* система не гарантирует смешной результат;
* большая степень повреждения может дать нечитаемую кашу;
* слишком сильная реконструкция может дать обычный фанфик;
* наиболее интересен баланс между повреждением и умеренным ремонтом;
* устойчивые мотивы могут оказаться случайными;
* наличие повторов само по себе не доказывает отдельную память модели.

## 23. Критерии готовности

Проект считается готовым, когда:

1. Устанавливается через `pip install -e .`.
2. Все тесты проходят.
3. Можно выполнить запуск только с mock-провайдерами без интернета.
4. Можно выполнить `translate_only`.
5. Можно выполнить режим с LLM-реконструкцией.
6. Можно включить rolling context.
7. Можно включить и выключить inferred memory.
8. Все поколения сохраняются.
9. Прерванный запуск продолжается.
10. Экспериментальная матрица сравнивает минимум четыре режима.
11. Создаётся читаемый отчёт.
12. В проекте нет заранее заданного псевдоканона.
13. Одни и те же seed и mock-провайдеры дают одинаковый результат.
14. README позволяет запустить пример без изучения исходного кода.

## 24. Порядок реализации

Работай итеративно.

Сначала:

1. изучи существующий репозиторий;
2. составь краткий план;
3. создай модели конфигурации;
4. реализуй mock-провайдеры;
5. реализуй chunking;
6. реализуй pipeline и checkpoints;
7. добавь CLI;
8. добавь основные режимы;
9. добавь отчёты и метрики;
10. затем добавь реальные провайдеры;
11. в последнюю очередь добавь экспериментальную память.

Не начинай с веб-интерфейса.

Не усложняй проект распределёнными очередями, базами данных и микросервисами. Для первой версии достаточно файловой системы и локального CLI.

После реализации:

* запусти тесты;
* запусти линтер и type checker, если добавлены;
* выполни демонстрационный запуск с mock-провайдерами;
* покажи созданные файлы;
* кратко перечисли сделанные архитектурные решения;
* отметь оставшиеся ограничения.

При неоднозначности выбирай наиболее простой расширяемый вариант и документируй допущение в README, не блокируя реализацию вопросами.
